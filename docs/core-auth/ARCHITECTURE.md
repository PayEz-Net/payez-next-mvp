# Core Authentication Architecture: `@payez/next-mvp`

**Version:** 2.0
**Status:** ✅ Active & Enforced
**Owner:** BAPert

## 1. Philosophy & Goals

This document details the "Golden Path" for authentication and session management within the `@payez/next-mvp` framework. The architecture is designed around three core principles:

1.  **Security First:** Session data, tokens, and user information must remain on the server. Client-side tokens (JWTs) should be opaque references, not containers of sensitive data.
2.  **Single Source of Truth:** A server-side Redis store holds all session information. This prevents data synchronization issues and allows for immediate session invalidation.
3.  **Seamless Developer Experience:** The complexity of the authentication flow should be abstracted away. Developers using the package should be able to secure an application with minimal, declarative configuration.

---

## 2. Core Components & Files

This system is composed of several key files within the `@payez/next-mvp` package, which work in concert with a few required files in the host application.

### Package Components (`@payez/next-mvp`)

| File Path | Purpose | Key Responsibilities |
| :--- | :--- | :--- |
| **`src/middleware/create-middleware.ts`** | **The Gatekeeper.** | Exports `createMvpMiddleware`, which generates the server-side middleware handler. It intercepts all incoming requests (pages and APIs) and is the first line of defense. |
| **`src/client/fetch-with-auth.ts`** | **The Client-Side Agent.** | Exports `fetchWithAuth`, a universal wrapper for `fetch`. It automatically injects the `Authorization` header into outgoing API requests and handles `401` responses by redirecting the user to the login page. |
| **`src/auth/auth-decision.ts`** | **The Logic Engine.** | Exports `makeAuthDecision`, a pure function that determines the outcome (allow or redirect) based on the route and session status. It is used by the middleware. |
| **`src/auth/route-config.ts`** | **The Public Access List.** | Exports `configurePublicRoutes` and `isUnauthenticatedRoute`. It provides a sophisticated, pattern-based way for the host application to define which routes do not require authentication. |
| **`src/lib/session-store.ts`** | **The Vault.** | Manages all interaction with the Redis session store. It provides functions for creating, reading, updating, and deleting sessions. This is the single source of truth for session data. |
| **`src/auth/auth-options.ts`** | **The Rulebook.** | (Future) Will export `createAuthOptions` to provide a complete, pre-configured `NextAuthOptions` object, abstracting away the complexities of Redis integration and JWT/session callbacks. |

### Host Application Components (`nexus.cryptaply`, etc.)

| File Path | Purpose | Key Responsibilities |
| :--- | :--- | :--- |
| **`src/middleware.ts`** | **Middleware Implementation.** | A simple file (3-5 lines) that imports and exports the handler generated by `createMvpMiddleware` from the package. It also defines the `matcher` config to specify which routes the middleware runs on. |
| **`src/app/api/session/viability/route.ts`** | **The Secure Session Check.** | A server-side API endpoint that uses the application's `authOptions` to securely check if a session is valid in Redis. It is called by the middleware to avoid exposing session logic to the edge. |
| **`src/lib/auth.ts`** | **Application Configuration.** | The file where the developer configures the application's specific authentication settings, such as calling `configurePublicRoutes` and defining the `authOptions`. |

## 3. Key Architectural Flows

### Flow 1: Authenticated User Accesses a Protected Page

*This flow describes a logged-in user navigating directly to `/dashboard/profile`.*

1.  **Request:** The user's browser sends a GET request for `/dashboard/profile`.
2.  **Middleware Intercepts:** The host application's `middleware.ts` catches the request. It calls the `createMvpMiddleware` handler from the `@payez/next-mvp` package.
3.  **Route Check:** The middleware uses `isUnauthenticatedRoute` to determine that `/dashboard/profile` is a protected route.
4.  **Session Viability Check:** The middleware makes a `fetch` call to its own internal `/api/session/viability` endpoint, forwarding the user's session cookie.
5.  **Redis Lookup:** The `/api/session/viability` handler uses `getSession` from the `session-store` to look up the session token in Redis. It finds a valid session.
6.  **Viability Response:** The API responds with `{ "authenticated": true }`.
7.  **Decision:** The middleware receives the `true` status and passes it to `makeAuthDecision`. The decision is **`'allow'`**.
8.  **Page Render:** The middleware allows the request to proceed, and the Next.js server renders and returns the profile page.

### Flow 2: Unauthenticated User Accesses a Protected Page

*This flow describes a new user navigating directly to `/dashboard/profile`.*

1.  **Request:** The user's browser sends a GET request for `/dashboard/profile`.
2.  **Middleware Intercepts:** The `middleware.ts` catches the request.
3.  **Route Check:** The middleware determines the route is protected.
4.  **Session Viability Check:** The middleware calls `/api/session/viability`.
5.  **Redis Lookup:** The API handler looks for the session token in Redis but finds nothing.
6.  **Viability Response:** The API responds with `{ "authenticated": false }`.
7.  **Decision:** The middleware receives the `false` status and passes it to `makeAuthDecision`. The decision is **`'redirect'`** with `location: '/account-auth/login?callbackUrl=%2Fdashboard%2Fprofile'`.
8.  **Server-Side Redirect:** The middleware returns a `307 Temporary Redirect` response to the browser, which immediately navigates to the login page.

### Flow 3: Authenticated User's Component Fetches API Data

*This flow describes a logged-in user on the profile page, where a component calls `useProfile()`.*

1.  **Client-Side Call:** The `useProfile` hook calls `fetchWithAuth('/api/account/profile')`.
2.  **Token Injection:** `fetchWithAuth` calls `getSession()` from `next-auth/react` to get the session, extracts the `accessToken`, and injects it into the `Authorization: Bearer <token>` header.
3.  **Request:** The browser sends a GET request for `/api/account/profile` with the auth header.
4.  **Middleware Intercepts:** The `middleware.ts` catches the API request.
5.  **Session Viability Check:** The middleware confirms the session is valid via `/api/session/viability` and Redis.
6.  **Decision:** The decision is **`'allow'`**.
7.  **API Route Handler:** The request proceeds to the `/api/account/profile` route handler, which validates the JWT and returns the user's profile data.
8.  **Response:** The component receives the data and renders it.

### Flow 4: Unauthenticated User's Component Fetches API Data

*This is the critical client-side redirect flow.*

1.  **Client-Side Call:** A component on a public page (or a page with a stale session) calls `fetchWithAuth('/api/account/profile')`.
2.  **Token Injection:** `fetchWithAuth` calls `getSession()`, finds no session, and sends the request without an `Authorization` header.
3.  **Request:** The browser sends the GET request for `/api/account/profile`.
4.  **Middleware Intercepts:** The `middleware.ts` catches the API request.
5.  **Session Viability Check:** The middleware determines the session is invalid via `/api/session/viability`.
6.  **Decision:** The decision is **`'redirect'`**.
7.  **401 Unauthorized Response:** Because the request was to an `/api/` route, the middleware **does not** perform a server-side redirect. Instead, it returns a `401 Unauthorized` JSON response: `{ "error": "Unauthorized" }`.
8.  **Client-Side Intercept:** The `fetchWithAuth` utility receives the `401` response.
9.  **Browser Redirect:** `fetchWithAuth` immediately executes `window.location.href = '/account-auth/login?callbackUrl=...'`, forcing a hard browser navigation to the login page.
10. **Execution Halt:** `fetchWithAuth` throws a specific `'UNAUTHORIZED_REDIRECT'` error to prevent any further client-side code (like React Query retries) from executing.

---

This comprehensive, multi-layered approach ensures that the application is secure by default, provides a consistent user experience, and remains easy for developers to use and maintain.
